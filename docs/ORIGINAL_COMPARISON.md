# 原版差异与回房状态核查（2026-11-23）

核查基线为 0.1.16、内部提交 `3ebdf2a`。本页前半部分保留 0.1.16 排查时的现象。0.1.17 已完成本地爬坡、聊天与回房修复并通过候选客户端验收，修复后的回房行为见 CHAT_AND_RETURN.md；表中技能差异仍未修改。线上部署结果独立记录于发行验收。

## 结算、返回、准备和下一局

用户连续报告“等待 1 位玩家返回”时准备和商城不可用，以及退出后大厅显示 3/8 人、对战中。本地纯内存复现场景已通过，不需要登录或改变线上对局。

| 触发条件 | 当前代码行为 | 原因与影响 |
| --- | --- | --- |
| 一人已返回，另一人仍在结算 | 已返回者的 `returned=true`；客户端禁用准备、商城、换车、地图和 AI 配置 | `main.gd` 的 `_update_room` 把“我已返回”直接当成所有配置不可操作的条件。服务器 `world.go` 的 ready、商城和换车入口也只看旧 `Battle` 是否仍存在，所以仅恢复按钮不足以修复。 |
| 全部真人返回，或最后一名未返回者离房 | `finishReturning` 清掉旧对局，并给所有成员写入 `Ready=true` | 所有人无需再点击准备，房主可以直接点开始。服务没有自动创建下一局的分支；必须收到房主的 `start` 命令。这是当前自动准备规则，不能把它描述成服务器自行开局。 |
| 已返回者离房，房主仍在结算，留下房主和两个 AI | 旧的、已经结束的 `Battle` 继续保留；大厅却显示“对战中”及 3/8 人 | 房间列表仅以 `Battle != nil` 生成 `started`，没有区分战斗和结算。因此第二张截图的“对战中”本身不能证明已开第二局。此状态已用同样的四人到三人顺序复现。 |
| 上述剩余房主完成返回，然后主动点开始 | 旧对局清掉；房主和 AI 已准备，可以创建三人新局 | 一个真人加 AI 符合当前开局条件；不依赖退出者再次准备。已单独验证开始前等待、离房释放及显式开局这三个步骤。 |

建议按玩家个人所处阶段解锁商城、换车及准备取消；旧结算可以继续为未返回者保留。开始仍由房主触发并校验所有真人返回、队伍及准备状态。最后一人返回时不要覆盖其他人刚调整的准备状态。大厅另行显示结算/等待返回，不能与真正对战共用同一个状态文案。

## 爬坡：本地已修复并核对

0.1.16 只从当前高度上方 22 像素找地面，再按绝对高度差 24 像素挡住；这遗漏了原版移动门禁，而且在厚墙里可能直接取得实体内部的像素。

原版 `00530210` / `00533f70` / `004d9410` 每横移一像素重新查询底盘支撑：朝上坡方向超过 65°、突然增加至少 40°、或单步抬高至少 5 像素会阻挡。普通车使用 15 像素宽底盘，9、19、29 号车使用 41 像素采样宽度。角度采用原始浮点值比较，不能用截断后的车身绘制角代替。

新实现让 Go 判定、本地预测及远端高度补帧共用相同底盘规则。仍保留既有防止直接走下悬崖的限制；没有把原版可迈出悬崖再逐刻掉落的整个回合物理链标为完成，也没有改动现有落体函数的默认角度算法。

原始只读程序 SHA-256：`1a517ff29965f27b42a2c7ed88a04031a4198fdbbbafd8f355d97ec4cff102d6`。`collect_native_walking.py` 用 Unicorn 执行其原始 x86 步行、支撑及角度函数，未替换这些函数；只代理数学 CRT、内存复制/清零与运行时检查。这种离线执行不是完整原版实机操作录像，边界必须区分。

| 本地验收 | 结果 |
| --- | --- |
| 原版 x86 对照 | 38 种左右镜像坡面、台阶和缺口，2296 个允许/阻挡、支撑位置及角度样本；Go 与 Godot 均匹配 |
| 最终候选导出包 | 隔离桌面、Dummy 音频下，2364 项原版样本及实际预测移动检查通过 |
| 真实注册、进房、按键行走及 250 毫秒迟到回包 | 150 项通过；松键后位置不回弹，预测位置、SP 和移动资源与服务一致 |
| 库存、护盾、传送和远端跨坡顶回归 | 92 项及 7380 个雷达像素检查通过 |
| Go 全量及静态分析 | 917 项含子测试通过，`go vet ./...` 通过 |

原版样本保存在 `源码/server/testdata/native-walking-oracle.json`。`qa_walking.py` 可在具备 Godot 的 Windows 环境重跑，不需要启动旧客户端。

| 车型/技能 | 原版证据 | 当前差异及复测重点 |

| 黑骑士（25）F3 | `00564720` / `00564910` 首次有效反弹把抓取半径放大至 100，再加车体半径 10，按整数距离小于 110 判断 | `native_reflection.go` 使用小于 15，漏抓落点旁的战车。需要复测 109/110 边界、多车及首次接地直接爆炸分支。 |
| 紫金刚（20）F2/F3 | `0055f470` / `0055fb50` 第一次越过地图顶边时派生继续飞行的子弹，原弹反射并增伤 | 当前 59 号飞行物走通用弹道，遗漏顶部派生分支。F3 三枚初弹都应独立验证。左右出图消失是用户明确要求，不能顺带恢复原版左右反弹。 |

## 已有证据支持，但不能标记全面等价

车载追踪弹的五枚导弹共 66 个从炮口到锁定的实录点重新比对，最大位置误差约 0.002 像素；追踪道具 21 个样本匹配。分裂载体及子弹、波形/旋转光束、反弹、手榴弹、吸收返还物的既有原版轨迹回归通过，但没有覆盖所有地形、目标组合、失活时序和多目标伤害。

救护/致盲半径、更多高级技能分支、远端跨复杂坡面时车身角度、房间过场逐帧时序以及部分附带粒子仍需继续采样，不能用“90 个武器能命中”代替原版逻辑等价证明。

用户明确保留的定制包括基础炮免费、初始 SP 150/行动后恢复 80、左右出界消失以及避免薄地形穿模；这些与原版有差别的行为应单独登记，不能作为普通差异直接回滚。
